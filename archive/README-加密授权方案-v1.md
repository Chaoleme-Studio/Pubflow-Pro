# PubFlow Pro 加密授权方案

本文记录当前版本的授权、加密、自定义协议和客户端保护边界。它面向后续开发和审计，优先说明哪些判断必须在服务端完成，哪些逻辑可以放在 WASM 或插件端执行。

## 设计目标

PubFlow Pro 的保护目标不是让浏览器插件端绝对不可逆，而是提高破解、复用和批量盗用成本：

- 激活码未激活前没有到期时间，只表示一份可售卖的授权库存。
- 激活发生在用户第一次输入激活码时，服务端记录插件安装标识、IP、时间、套餐和来源。
- 日常启动时由服务端验证 lease token、插件安装标识、过期时间、吊销状态和策略版本。
- 高价值 selector 不随插件静态分发，由服务端按授权动态下发。
- 首次激活使用 PFAP 二进制协议封装，避免抓包直接看到激活码和安装实例 ID。
- selector 请求使用 PFSP 自定义二进制封装，避免抓包后直接看到明文 JSON 或可读业务协议。
- WASM 负责协议编解码和加解密执行，但不作为最终授权权威。

## 模块边界

```text
pubflow-core
  授权签名、设备哈希、selector 加密、PFAP/PFSP 协议。纯库，供 app/wasm/native 复用。

app
  Axum 服务端。激活码生命周期、lease 签发和验证、selector 下发、后台管理都在这里完成。

pubflow-wasm
  浏览器插件加载的 WASM。用于 PFAP/PFSP 请求构造、响应解码、selector 二次解密和部分本地工具函数。

pubflow-native
  Native Messaging helper。读取系统机器码并生成设备哈希。构建时必须注入 MACHINE_SALT。

pubflow-Pro
  Chrome 扩展。用户只输入激活码；插件自动保存 lease token、服务端配置和加密后的本地状态，不保存服务端私钥。
```

## 激活码生命周期

系统支持两种购买渠道：

- 官网订单：用户在网页购买，订单关联激活码。
- 第三方平台：管理员批量生成激活码，放到第三方平台作为库存售卖。

激活码生成时只应有创建时间、套餐、来源、批次等库存信息，不应立即写入到期时间。到期时间从首次激活开始计算，未激活状态在后台应显示为“未激活”。

首次激活时，插件通过 PFAP 提交激活码和内部安装实例 ID。服务端检查激活码是否存在、未吊销、未超过安装数量限制，然后绑定安装实例并签发 lease token。后续启动不再信任客户端自己判断授权状态，而是向服务端验证。

当前订阅版绑定的是浏览器插件安装实例，不是硬件 Machine Hash。数据库新字段使用 `client_install_id`；旧 `machine_hash` 字段仅作为历史兼容列保留，不再承载订阅授权语义。永久版硬件绑定后续另行设计。

当同一个激活码达到 `max_devices` 上限后，新安装实例激活会自动吊销旧 active leases，并为当前安装实例签发新 lease。这避免用户换电脑或重装浏览器后必须手动找客服，同时后台授权记录会保留自动踢旧事件。

## Lease Token

Lease token 当前使用 JWT HS256，由服务端签发和验签。客户端可以持有 token，但不能把未验签 payload 作为安全决策依据。

服务端验证内容包括：

- JWT 签名是否有效。
- token 是否过期。
- license 是否存在、是否吊销。
- 激活码是否仍有效。
- 插件安装实例 ID 是否匹配。当前版本不使用真实硬件设备码；永久版再单独设计 Native/硬件绑定方案。
- 策略版本、最低插件版本和套餐权限是否满足。
- 授权请求记录，包括来源 IP、安装实例、结果和失败原因。

WASM 中不再导出 `verify_lease`。原因是客户端没有服务端 JWT secret，无法可靠验签；只解析 JWT payload 会让伪造的 token 看起来有效，容易误导后续开发。

## License 签名

`pubflow-core` 的 License 签名使用 Ed25519。当前签名消息采用 `pubflow-license-v2` 域分隔前缀，并对每个字段加入长度前缀：

```text
domain || len(device_id) || device_id || len(tier) || tier || len(expires_at) || expires_at || len(activation_code) || activation_code
```

这样可以避免字段直接拼接导致的边界模糊。注意：该格式与旧的无分隔符签名消息不兼容，旧签名需要重新签发。

## PFAP/PFSP 自定义协议

PFAP 用于首次激活，PFSP 用于 selector 拉取。它们不是替代 HTTPS，而是在 HTTPS 之上增加一层应用协议保护，避免抓包后直接得到清晰的 REST JSON 结构。

当前设计要点：

- 客户端每次请求生成临时 X25519 密钥对。
- 服务端使用自己的长期公钥参与密钥协商。
- HKDF 派生 request key 和 response key，请求和响应密钥分离。
- AAD 绑定协议版本、上下文、时间戳和 nonce。
- 请求体使用二进制 envelope 承载，内部再放业务 payload。
- 服务端检查时间窗口，并通过 Redis 记录 nonce 防重放。
- 响应体使用会话 response key 加密，插件端通过 WASM 解码。

这能防止“抓一次包直接复用激活请求或 selector 响应”的低成本攻击。攻击者即使看到 HTTPS 解密后的流量，也需要理解协议 envelope、临时密钥、AAD、nonce 和响应密钥派生过程。

## Selector 保护

selector 是插件端最有价值的业务资产之一，尤其是平台 DOM 定位、发布流程细节和平台差异化规则。

保护策略：

- 高价值 selector 不写死在插件包中。
- 服务端数据库保存加密 selector。
- 插件启动并通过授权验证后，使用 PFSP 请求 selector。
- PFSP 响应保护传输层内容。
- selector JSON 还会按激活码派生密钥做二次加密，避免本地缓存出现明文。
- 插件只在运行时短暂持有解密结果。

低价值的通用平台流程、UI 展示、类型定义可以留在插件端。平台核心 selector、授权策略、套餐功能开关、版本封禁策略、吊销状态必须放服务端。

## Native 设备码

Native helper 读取系统级机器码后，用 `SHA-256(MACHINE_SALT + ":" + raw_machine_id)` 生成设备哈希。生产构建必须提供稳定且私密的 `MACHINE_SALT`。

当前源码和 `scripts/build-native.sh` 已不再提供默认盐值。缺少 `MACHINE_SALT` 时构建会失败，避免生产包静默使用可预测盐。

## 客户端存储边界

插件端可以保存：

- 激活码。
- 自动签发的 lease token。
- 浏览器插件安装实例 ID。
- 构建时注入的服务端地址和基础配置。
- 加密后的 selector 缓存。
- 加密后的用户本地设置。

插件端不应保存：

- JWT 签名 secret。
- License Ed25519 私钥。
- selector 服务端主密钥。
- 管理员 token 或后台凭证。
- 可独立绕过服务端验证的授权判断逻辑。

## 已知限制

浏览器扩展运行在用户设备上，客户端代码、WASM 和运行时内存都可以被有经验的攻击者分析。该方案的实际目标是降低批量破解、抓包复用、静态提取 selector 和伪造设备授权的成功率。

对抗更强攻击时还需要继续加强：

- 更细粒度的授权记录和异常风控。
- selector 按平台、版本和套餐拆分下发。
- 关键发布流程增加服务端策略开关。
- 插件端运行时完整性和调试环境检测。
- 管理后台操作审计和多管理员权限模型。
